# Gateway Error Response Customization — Design

**Status:** Approved in principle (design-review answers recorded in §8) — implementation to follow the companion plan `error-response-customization-plan.md`. Global configuration is the first slice.
**Date:** 2026-06-23
**Author:** (design review follow-up)
**Related:** SOAP Fault formatter (`policy-engine/internal/kernel/soap_fault.go`), issue [#1637](https://github.com/wso2/api-platform/issues/1637), plan `docs/gateway/error-response-customization-plan.md`

## Design-review decisions (2026-06-23)

- Error-category taxonomy is approved **on the condition that it works with analytics disabled** — satisfied; the taxonomy is defined independently of the analytics module (§4.1.1).
- Configuration shape approved.
- Phasing approved; **global error configuration is implemented first** (within Phase 1).
- **New requirement:** error responses must be configurable following **OpenAPI standards** — the config surface uses the OpenAPI *Responses Object* / *Media Type Object* shape (§4.2).

---

## 1. Problem statement

Today the gateway's error responses are **rigid**:

- Gateway-generated errors (auth failure, throttling, no route, malformed request, internal policy errors) return **fixed status codes and fixed bodies** baked into the code (e.g. `{"error":"Internal Server Error"}`, `{"error":"Not Found"}`, `{"error":"forbidden"}`).
- Envoy-generated errors (backend unreachable, upstream timeout, payload too large, no healthy upstream) return **Envoy's default body** with **no customization**.
- Backend error responses pass through, but there is no consistent way to reshape them.

The design review raised a new requirement:

> Users should be able to customize, **globally and per-API**, the error **messages** and **status codes** the gateway returns for both **gateway-generated** and **backend** errors.

The recently added SOAP Fault formatter is the first instance of error-shaping in the gateway. It is the proof that a central, metadata-driven error transformation is achievable; this design generalizes that idea.

**This document assesses feasibility (conclusion: feasible) and proposes a phased implementation. No code is written until the design is approved.**

---

## 2. Where errors come from today

Errors originate in **three distinct places**, and each requires a different customization mechanism. This is the single most important fact for the design.

| # | Error source | Examples | Travels through policy engine? | Customizable today? |
|---|--------------|----------|-------------------------------|---------------------|
| **A** | **Gateway policy-generated** (`ImmediateResponse`) | auth 401/403, throttle 429, subscription invalid, malformed body 400, policy exec 500, no-policy-chain 500 | **Yes** — short-circuits via ext_proc | No (fixed bodies) |
| **B** | **Backend response** | backend app returns 4xx/5xx with its own body | **Yes** — response phase ext_proc | Only by writing a custom policy |
| **C** | **Envoy local reply** | 503 no healthy upstream, 504 upstream timeout, 413 payload too large, 426 upgrade, **404 no-route** (DirectResponse) | **No** — generated by Envoy before/around ext_proc | No |

### 2A. Gateway policy-generated errors (the core case)

Every gateway-generated `ImmediateResponse` funnels through a **small set of choke points** that already call `applySOAPFaultFormat(...)`. Confirmed call sites:

- `internal/kernel/translator.go` — 6 sites (request/response header & body short-circuit + bodyless merge paths): lines ~67, ~363, ~525, ~748, ~850, ~1089
- `internal/kernel/execution_context.go:179` — `handlePolicyError` (central handler for all policy execution failures, all phases)
- `internal/kernel/extproc.go:176` — no-policy-chain-found error

The `policy.ImmediateResponse` struct (`sdk/core/policy/v1alpha2/action.go`) carries `StatusCode`, `Headers`, `Body`, plus analytics/dynamic metadata. Because **every** gateway error already passes `applySOAPFaultFormat`, we have a natural, proven choke point to generalize.

> Note: the actual 401/403/429 bodies are produced by the **auth and ratelimit policies**, not the kernel. But they all return an `ImmediateResponse` that flows through the same choke points. Customizing **at the choke point, keyed by status code / error category** means we do **not** have to touch each individual policy.

### 2B. Backend errors

Backend responses (including 4xx/5xx the backend app produces) flow through the response-header / response-body ext_proc phases (`execution_context.go` `buildResponseContexts`, `processResponseHeaders`, `processResponseBody`). A policy can already read and modify them. There is currently **no flag distinguishing a backend response from an Envoy local reply** at the engine (see §6).

### 2C. Envoy local replies — the gap

When the backend is unreachable / times out / the request is rejected by Envoy itself, **Envoy emits a "local reply" that never reaches the policy engine**. The no-route case is an Envoy `DirectResponse` (`translator.go:490-519`, body hardcoded `{"error":"Not Found"}`, ext_proc explicitly disabled on that route).

These can **only** be customized via Envoy's [`local_reply_config`](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_conn_man/local_reply) on the `HttpConnectionManager`. There is already a **commented-out template** in `policy-engine/configs/envoy.yaml:39-55` and the controller builds the HCM in `translator.go createListener()` (~line 1055) but does **not** set `LocalReplyConfig` today. `local_reply_config` is **listener/HCM-scoped**, so it is naturally a **global** customization; per-API local-reply customization requires response-map filters matching a route header and is materially harder (see §8, Phase 4).

---

## 3. Feasibility conclusion

**Feasible.** Evidence:

1. The SOAP Fault formatter already demonstrates central, metadata-driven error reshaping for source **A**.
2. Per-API configuration already flows to the engine via policy-xDS route metadata (`pkg/policyxds/snapshot.go createRouteConfigResource` → `RouteMetadata` → `SharedContext`). Adding an `error_config` field to that metadata is a well-trodden path.
3. Global config already has a TOML home (`gateway/configs/config-template.toml`) and a controller config struct (`pkg/config/config.go`).
4. Envoy local-reply customization is a built-in Envoy feature with a ready template in-repo.
5. An existing TODO (#1637) explicitly defers "error codes" to a dedicated effort — this is that effort.

The work splits cleanly along the three error sources, which lets us phase it.

## 4. Proposed design

### 4.1 Error taxonomy (the contract)

Define a stable set of **error categories** so users configure semantics, not brittle internals. Proposed initial set:

| Category key | Default status | Source | Trigger |
|--------------|---------------|--------|---------|
| `AUTHENTICATION_FAILURE` | 401 | A | auth policy rejects credentials |
| `AUTHORIZATION_FAILURE` | 403 | A | scope/role/subscription denied |
| `THROTTLED` | 429 | A | rate limit / quota exceeded |
| `REQUEST_MALFORMED` | 400 | A | bad body / envelope |
| `ROUTE_NOT_FOUND` | 404 | C | no matching API |
| `INTERNAL_ERROR` | 500 | A | policy exec failure / no chain |
| `BACKEND_UNAVAILABLE` | 503 | C | no healthy upstream / connect fail |
| `BACKEND_TIMEOUT` | 504 | C | upstream timeout |
| `PAYLOAD_TOO_LARGE` | 413 | C | request exceeds limit |
| `BACKEND_ERROR` | (passthrough) | B | backend returned 4xx/5xx |

For source **A**, the category is derived from the `ImmediateResponse` status code, optionally refined by an error-category hint the policy may set in `DynamicMetadata`/`Headers` (backward-compatible: status-code mapping works without any policy changes). For source **C**, the category maps from Envoy **response flags** (`UH`/`UF`→`BACKEND_UNAVAILABLE`, `UT`→`BACKEND_TIMEOUT`, etc.).

### 4.1.1 Independence from analytics (design-review requirement)

There is already a fault taxonomy in the codebase, but it belongs to the **analytics module** and is **not** what this feature uses:

- `internal/analytics/analytics.go` — `FaultCategory` (`TARGET_CONNECTIVITY`, `OTHER`)
- `internal/analytics/constants.go` — the `900800`-series `ErrorCode` constants (throttle/blocked codes) and `dto/error.go` (`FaultSubCategory`)

Those describe **analytics events** and are consumed by the analytics/ALS pipeline.

This feature's error-response taxonomy (§4.1) is a **separate concept**, and its enforcement is **independent of analytics** for two reasons:

1. **Enforcement point.** Error responses are shaped at the kernel `ImmediateResponse` choke points (`translator.go`, `execution_context.go` `handlePolicyError`, `extproc.go`) and, for Envoy local replies, inside Envoy's `local_reply_config`. Neither depends on the analytics **system policy** being attached to the chain, nor on `[analytics] enabled` in config. Every request passes these choke points regardless of analytics state.

2. **No code dependency.** The error-category constants will live in their **own package** (proposed: `policy-engine/internal/kernel/errorformat` + a mirror in the controller), *not* imported from `internal/analytics`. Turning analytics off (or removing the analytics system policy) has **zero effect** on error customization.

**Correlation without coupling.** For operators who also run analytics, the two taxonomies map cleanly — documented as a reference table, implemented as a small pure mapping function (no shared types):

| Error-response category | Analytics `FaultCategory` (for correlation only) |
|-------------------------|--------------------------------------------------|
| `BACKEND_UNAVAILABLE`, `BACKEND_TIMEOUT` | `TARGET_CONNECTIVITY` |
| `THROTTLED` | `OTHER` (+ `900800`-series `ErrorCode`) |
| `AUTHENTICATION_FAILURE`, `AUTHORIZATION_FAILURE`, `REQUEST_MALFORMED`, `ROUTE_NOT_FOUND`, `INTERNAL_ERROR` | `OTHER` |

This mapping is optional and one-directional; error customization never reads analytics state.

### 4.2 Configuration model (OpenAPI-standard)

Per the design-review requirement, the configuration surface follows the **OpenAPI 3.x Responses Object**: a map **keyed by HTTP status code** (plus `default`), where each entry is a subset of the OpenAPI **Response Object** — `description` and a `content` map of **Media Type Objects** (`schema`, `example`/`examples`). This is standard, tooling-friendly, and gives content negotiation for free.

**Why status-code keys (not category keys).** OpenAPI keys responses by status code, so the user-facing surface does too. The semantic **categories** (§4.1) remain an internal mechanism: they classify each gateway/Envoy error and select the **default status code**, which is then used to look up the matching response entry. A category may also be surfaced as an `x-error-category` extension on a response entry for operators who want to remap by semantics (optional).

**What the gateway renders.** The gateway returns the media type's **`example`** (with placeholder substitution, §4.4). `schema` is treated as **descriptive/validation-only** — it documents the body but is not required to produce one. `examples` (plural, keyed) is supported; the first or a named default is used.

**Status override.** By default the response entry's key *is* the returned status. To remap (e.g. return `502` where Envoy would emit `504`), an entry may carry `x-status-code-override` (an OpenAPI spec extension, keeping the document valid).

**Global** — an OpenAPI-shaped YAML document referenced from `config-template.toml` (koanf already supports file providers; keeping OpenAPI shape in YAML rather than TOML avoids awkward nesting):

```toml
[error_handling]
  enabled = true
  config_file = "conf/error-responses.yaml"   # OpenAPI-shaped, see below
  default_media_type = "application/json"      # used when Accept doesn't match
```

```yaml
# conf/error-responses.yaml  — OpenAPI Responses Object
responses:
  "401":
    description: Authentication failure
    content:
      application/json:
        schema: { $ref: "#/components/schemas/Error" }
        example: { code: 401, message: "Authentication required", requestId: "{{requestId}}" }
      application/xml:
        example: "<error><code>401</code><message>Authentication required</message></error>"
  "429":
    description: Rate limit exceeded
    content:
      application/json:
        example: { code: 429, message: "Too many requests" }
  "503":
    description: Backend unavailable
    content:
      application/json:
        example: { code: 503, message: "Service temporarily unavailable" }
  "504":
    description: Upstream timeout
    x-status-code-override: 502            # optionally remap 504 → 502
    content:
      application/json:
        example: { code: 502, message: "Upstream did not respond in time" }
  default:
    description: Fallback for any error status not explicitly listed
    content:
      application/json:
        example: { code: "{{statusCode}}", message: "{{message}}", requestId: "{{requestId}}" }
components:
  schemas:
    Error:
      type: object
      properties:
        code:    { type: integer }
        message: { type: string }
        requestId: { type: string }
```

**Per-API** (API CRD spec — `RestAPIData`, `SoapAPIData`, etc., new optional `errorResponses` field) — the **same** OpenAPI Responses Object shape:

```yaml
spec:
  errorResponses:
    responses:
      "401":
        description: Custom auth message for StockQuote
        content:
          application/json:
            example: { error: "Provide a valid API key for StockQuote" }
      "504":
        x-status-code-override: 502
        content:
          application/json:
            example: { error: "Upstream slow, try later" }
```

**Precedence:** per-API response entry → global response entry → global `default` → built-in hardcoded default. Resolution is **per status code**; a per-API override of `401` does not affect the global `429`. Within an entry, `content` media types are negotiated against the request `Accept` header, falling back to `default_media_type`.

### 4.3 Where configuration is applied

| Source | Applied where | Config delivery |
|--------|---------------|-----------------|
| **A** (policy errors) | New central function `applyErrorFormat(immResp, execCtx)` in policy engine, invoked at the **same 8 choke points** as (and immediately before) `applySOAPFaultFormat` | Per-API via route metadata (`SharedContext.ErrorConfig`); global via engine startup config |
| **B** (backend errors) | A new opt-in **system response-phase formatter** (or extension of the choke point on the response phase), gated by per-API `errorResponses.BACKEND_ERROR` | Same as A |
| **C** (Envoy local replies) | Envoy `local_reply_config` injected into the HCM in `createListener()`; custom no-route `DirectResponse` body | Global via controller config; per-API deferred to Phase 4 |

### 4.4 Body templating & content negotiation

The rendered body comes from the negotiated media type's `example` (serialized to the media type: JSON for `application/*json`, string for XML/text). A minimal, safe placeholder syntax (no arbitrary code execution) is substituted into `example` string values:

- `{{statusCode}}`, `{{message}}`, `{{errorCode}}`, `{{category}}`, `{{requestId}}`, `{{apiName}}`, `{{apiVersion}}`.
- **Media type** chosen by: request `Accept` header match against the entry's `content` keys → global `default_media_type` → the entry's first media type.
- Placeholder values are escaped per media type (JSON-escape vs XML-escape) to avoid injection; body size is capped.
- `schema` is descriptive only (documents/validates the shape); the gateway does not synthesize a body from `schema`.

### 4.5 Composition with the SOAP Fault formatter

The SOAP formatter stays, but the **order becomes**: `applyErrorFormat` (resolve status + message/body from config) **→** `applySOAPFaultFormat` (if `APIKind == SoapApi` and the body isn't already XML, wrap the resolved message into a SOAP Fault of the negotiated dialect). This means a SOAP API's customized message is carried into the fault `<faultstring>`/`<Reason>` rather than being a separate code path. The existing "already-XML ⇒ leave alone" guard lets a user supply a full custom fault body if they want.

## 5. Phased implementation plan

Each phase is independently shippable and testable. **Detailed, step-by-step tasks live in the companion plan `docs/gateway/error-response-customization-plan.md`.** The summary below is the shape; the plan is the source of truth for tasks/ordering.

> Ordering note (design-review): **global configuration is built first** within Phase 1, then per-API layers on top.

### Phase 0 — Taxonomy + OpenAPI config schema (no behavior change)
1. Define the error-category constants in their **own package** (independent of `internal/analytics`, per §4.1.1) in both controller and engine, plus the pure category→analytics-FaultCategory correlation mapping.
2. Add the `[error_handling]` section to `config-template.toml` (`enabled`, `config_file`, `default_media_type`) and a struct in `pkg/config/config.go`; parse the referenced OpenAPI-shaped YAML into a validated in-memory model (no application yet).
3. Add the optional `errorResponses` field (OpenAPI Responses Object subset) to `SoapAPIData` / `RestAPIData` (and other kinds) in `management-openapi.yaml`; regenerate `generated.go`; validate (status keys in 100–599 or `default`, known media types, `x-status-code-override` range, body/example size cap).
4. **Decision checkpoint:** confirm taxonomy + OpenAPI shape (recorded — see §8).

### Phase 1 — Gateway policy errors (source A): **global first, then per-API** — *highest value*
1. **Global:** deliver the parsed global error-response model to the engine (startup config, mirroring existing engine config loading). Implement `applyErrorFormat(immResp, execCtx)` in a new `internal/kernel/errorformat` package: resolve status (+ optional category hint) → look up global response entry → negotiate media type → render `example` with placeholders / apply `x-status-code-override`.
2. Invoke `applyErrorFormat` at the **8 choke points**, immediately before `applySOAPFaultFormat`; reorder composition per §4.5.
3. **Per-API:** thread `errorResponses` into policy-xDS route metadata (`createRouteConfigResource` in `pkg/policyxds/snapshot.go`) → extend `RouteMetadata` / `SharedContext`; apply per-API → global → default precedence in `applyErrorFormat`.
4. Tests: unit tests for resolution/precedence/negotiation/templating; kernel tests asserting customized bodies at each choke point; SOAP composition test; "analytics disabled" test proving independence.

### Phase 2 — Envoy local replies, global (source C)
1. Add controller config for local-reply customization; build a `LocalReplyConfig` in `createListener()` from it (uncomment/parametrize the `envoy.yaml` template) mapping response flags → category bodies/status.
2. Replace the hardcoded no-route `DirectResponse` body (`translator.go:490-519`) with the configured `ROUTE_NOT_FOUND` body.
3. Tests: xDS golden tests for the generated HCM `local_reply_config`; IT test forcing 503/504/413/404.

### Phase 3 — Backend error reshaping (source B)
1. Add an opt-in response-phase path that, when `errorResponses.BACKEND_ERROR` is set, reshapes backend 4xx/5xx (e.g. mask 5xx bodies). Must distinguish backend responses from local replies (see §6).
2. Tests: backend returns 500 with body → gateway returns configured shape; passthrough when not configured.

### Phase 4 — Per-API local replies (optional / stretch)
- Per-API customization of Envoy-generated errors via response-map filters keyed on a route-injected header carrying the API id. Higher complexity; ship only if there is demand.

## 6. Distinguishing backend errors from gateway errors (needed for Phase 3)

The engine cannot today tell a backend 503 from Envoy's "no healthy upstream" 503. Options:

1. **Envoy response flags via header:** add `x-wso2-response-fault-flag: %RESPONSE_FLAGS%` (the commented template already shows this) on local replies, or surface flags to ext_proc. Empty flag ⇒ genuine backend response.
2. **Source A is unambiguous:** gateway policy errors are produced inside the engine, so they're already known to be gateway-origin.

Phase 1 does not need this; Phase 3 does. Recommend resolving via option 1.

---

## 7. Backward compatibility & safety

- All config is **optional**; with nothing configured, behavior is **identical** to today (built-in defaults).
- No policy SDK changes required for Phase 1 (status-code keyed) — keeps the published SDK stable; the optional category hint is additive.
- Templating is placeholder-substitution only — no code execution, bounded body size, escaped values → no injection risk.
- Streaming caveat: mid-stream errors (`FULL_DUPLEX_STREAMED`) cannot emit a clean body (Envoy resets the stream); error customization does not apply there. Document this limitation.
- Status-code overrides validated to a sane range; warn if a category is overridden to a non-error status.

## 8. Design-review resolutions (2026-06-23)

1. **Category set (§4.1):** ✅ Approved — **conditional on working with analytics disabled**. Satisfied: the taxonomy is defined in its own package, independent of `internal/analytics`, and enforced at points that run regardless of analytics state (§4.1.1).
2. **Config surface:** ✅ Approved, **superseded by the OpenAPI requirement** — the config is the OpenAPI **Responses Object** keyed by HTTP status code (§4.2), not a category-keyed map. Categories remain internal.
3. **Scope / phasing:** ✅ Approved (A → C → B → per-API local replies). **Within Phase 1, global configuration is implemented first**, then per-API.
4. **OpenAPI standard (new requirement):** ✅ Error responses are configured using the OpenAPI Responses Object / Media Type Object shape, with `Accept`-based content negotiation (§4.2, §4.4).
5. **Backend error reshaping (source B):** kept in the plan as **Phase 3** (later); not part of the initial global slice.
6. **SOAP composition:** §4.5 ordering (custom message wrapped into SOAP Fault) stands.

Remaining minor items (can be settled during Phase 0 implementation, non-blocking): exact placeholder set, body-size cap value, and whether `examples` (plural) is supported in v1 or deferred.
